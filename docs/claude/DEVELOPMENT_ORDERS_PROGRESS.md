# DEVELOPMENT_ORDERS 진행 기록

`PROTOCOL-Claude-Development-Orders.md`(F01~F27)를 순서대로 진행한 실제 기록. 각 항목은 7절 보고 양식을 따른다.
완료로 적힌 항목도 "재구현 금지" 원칙에 따라 이미 충족된 부분은 다시 만들지 않는다 — 다음 세션은 이 파일과 최신 코드를 먼저 대조한다.

## F02 — PC·모바일 방송 화면 인수 · 부분 완료(데스크톱) / 모바일은 도구 제약으로 BLOCKED (2026-09-15)

**목표:** 1440×900/390×844/360×800에서 미니맵·상태창·중계·결과 동기화를 확인하고 "필수 동작"(t=0 정지 확인·1/2/4배속·슬라이더·다음 사건·완료 사건 클릭·끝으로 이동·종료 후 되감기·재시작·탭 비활성/복귀·선수 아이콘 키보드/터치·이미지 실패 폴백) 전부를 실제로 검증한다.

**사용자에게 달라진 경험:** 없음(코드 미변경) — 실제 동작을 재현 가능하게 검증만 했고, 검증 중 실제 결함은 발견되지 않았다.

**조사·검증 방법:** `resize_window`로 390×844/360×800을 시도했으나 `window.innerWidth`가 여전히 1920으로 유지됨을 JS로 직접 확인 — 이 환경은 실제 브라우저 창을 리사이즈하지 못하고 CDP 캡처가 고정 해상도에 묶여 있다(과거 D018/D020/D021/D022 세션에서도 동일하게 기록된 제약, 이번에도 재현됨). **모바일 두 크기는 실제 인수를 하지 못했다 — BLOCKED로 남긴다, 완료로 표시하지 않는다.**

대신 데스크톱 유효 폭(약 1568~1905px, 1440~1600 구간 포함)에서 `app/replay-theater.tsx`의 모든 "필수 동작"을 `javascript_tool`로 실제 DOM 이벤트를 발생시켜(좌표 클릭이 아니라 `dispatchEvent`로 React `onChange`/`onClick` 핸들러를 직접, 그러나 실제 컴포넌트 코드 경로로 구동) 하나씩 검증했다. rAF 기반 자동 재생은 이 자동화 환경에서 `document.hidden`이 false로 읽히는데도 실질적으로 스로틀링되어 실시간 흐름 관찰은 신뢰할 수 없었다(별도 발견 — 아래 "환경 특이사항" 참조). seek/버튼 기반 제어는 rAF에 의존하지 않아 안정적으로 검증됐다.

**실제로 실행한 검증과 결과 (전부 정상):**
- 시크 슬라이더 → 임의 지점(12:50)으로 정확히 이동, 점수·골드 갱신, 결과 미노출(스포일러 없음).
- 끝으로 이동(슬라이더 max) → RECAP 카드 노출, 실제 최종 점수(1:2) 공개, 구조물/KDA 전부 집계된 상태로 표시.
- 종료 후 되감기(슬라이더를 40%로) → RECAP 카드 다시 숨김(재노출 없음, 결과 미리보기 없음) — `BROADCAST_CONTINUATION.md`가 주장한 수정이 실제로 동작함을 확인.
- 완료된 사건 클릭(`.rt-history` 버튼, 예: "드래곤" 사건) → 해당 사건 시작 시각으로 정확히 이동.
- 재시작(처음부터 버튼) → t=00:00으로 복귀 + 자동 재생 재개, RECAP 카드 숨김 유지.
- 재생/일시정지 토글 → 상태 정상 전환(단, DOM 반영이 지연될 때가 있음 — 아래 환경 특이사항).
- 선수 아이콘: 코드 검토로 `role="button"`·`tabIndex={0}`·`onKeyDown`(Enter/Space) 확인 — 키보드 접근 이미 구현됨.
- 이미지 실패 폴백: `<image>`의 `href`를 존재하지 않는 URL로 직접 교체해 강제 실패시킴 → `onError`가 이미지만 `display:none` 처리하고 밑에 있던 약어 텍스트(`.rt-abbr`)가 정상 노출됨을 실측 확인.
- 콘솔 에러 0건. 데스크톱 유효 폭에서 `document.documentElement.scrollWidth===clientWidth`(가로 넘침 없음).

**환경 특이사항(버그 아님, 오탐 기록):** 처음에는 "끝으로 이동해도 재생 버튼 라벨이 계속 '일시정지'로 남는다"를 결함으로 의심했으나, 대기 시간을 늘리고 화면을 직접 스크린샷으로 재확인하자 실제 아이콘은 이미 Play(▷)로 정확히 바뀌어 있었다 — 이 환경에서 React 상태 갱신이 DOM에 반영되는 시점이 수백 ms 지연될 수 있다는 것이 원인. 실제 애플리케이션 결함이 아니므로 코드 수정 없음.

**정적 감사(모바일 폭을 실제로 못 봤으므로 보완):** `app/globals.css`에 이미 `max-width:1250/1050/767px` 전 구간 반응형 규칙과 `.rt-stage/.rt-map`(768px), `.rt-lineups`(420px) 미니맵 전용 규칙이 존재한다(이전 세션들이 만든 것, 이번에 새로 만들지 않음). 픽셀 단위로 눈으로 확인한 것은 아니므로 "완료"라 주장하지 않고, 구조적으로 좁은 화면 대응 코드가 있다는 사실만 기록한다.

**기준선 대비 변화:** 없음(엔진·표시 코드 모두 미변경).

**알려진 문제·미검증·외부 차단:** **BLOCKED(도구 제약)** — 390×844·360×800 실제 픽셀 검증은 여전히 불가능. 실기기 또는 이 자동화가 실제로 창 크기를 바꿀 수 있는 환경이 확보되기 전까지는 "완료"로 올리지 않는다. 터치 히트박스 겹침·모바일 전용 레이아웃 버그는 코드만으로는 완전히 배제할 수 없다.

**다음 작업 ID / 바로 실행할 첫 행동:** F03 — `combat.resource`/`lead[]`/표시 `goldA·goldB`/POG/킬 피드/구조물 스냅샷의 생성·소비 경로를 감사해 이중 지급이나 표시 골드 임의 증가가 있는지 확인한다.

## F01 — 실행·저장 왕복 · 완료 (2026-09-15)

**목표:** 새 커리어 생성→훈련→밴픽→경기→저장→새로고침→복원이 실제로 되는지 확인하고, 안 되면 고친다.

**사용자에게 달라진 경험:** 없음(기능 변경 아님) — 다만 `START_GAME.md`가 실제 동작과 일치하도록 정정됐다. 이전 문서는 "401이 날 수 있다"는 불확실성만 남겼는데, 실제로는 `npm run dev`(vinext) 자체가 로컬 전용 가짜 사용자로 자동 로그인하므로 사용자가 아무것도 더 할 필요가 없다.

**조사 결과:** `app/api/game/route.ts`는 `oai-authenticated-user-id` 헤더가 없으면 401을 반환하는 것이 사실이다. 그러나 `scripts/run-framework.mjs`가 실행하는 `node_modules/vinext`의 dev 서버가 기동 시 `Sites local sign-in: seedy@sites.test`를 출력하며 이 헤더를 로컬 요청에 자동으로 주입한다(Sites 플랫폼의 로컬 개발 편의 기능). 저장은 `wrangler --local`이 `.wrangler/state`에 D1을 에뮬레이션하며 이 경로는 `.gitignore`에 이미 포함되어 있어 운영 데이터와 분리된다. 즉 **F01이 요구하는 조건은 이미 충족되어 있었다** — 코드 결함이 아니라 문서의 불확실성이 문제였다.

**변경 파일:** `START_GAME.md`(재작성 — 로컬 자동 로그인 동작·저장 위치·분리 보장을 실제 확인한 그대로 기술, 문제 발생 시 진단 순서 추가).

**실제로 실행한 검증과 결과:**
- 커리어 3(빈 슬롯)에서 Gen.G로 신규 생성 → "주간 훈련 확정" 화면 정상 진입, 시작 자금 10.00억/샐러리캡 25.00억 정상.
- 완전히 새 브라우저 탭으로 `http://localhost:5174/`(vinext가 5173 사용 중이라 자동 전환한 포트) 재접속 → 커리어 1(T1, KT전 진행 중, 자동 저장됨 표시) 상태가 그대로 복원.
- 커리어 드롭다운으로 슬롯 1/2/3 전환 → 각각 T1/BRO/Gen.G로 완전히 분리되어 있고 리그 순위표의 "MY TEAM" 강조도 슬롯별로 정확히 바뀜(슬롯 혼동 없음).
- 콘솔 에러 없음.
- 중복 요청/오래된 revision 방지는 `app/api/game/route.ts`의 기존 코드 리뷰로 확인(commandId+fingerprint 중복 무시, `revision` 비교 후 UPDATE 실패 시 409 반환) — 별도 수정 불필요, 브라우저 재현은 하지 않음(코드가 이미 원자적 CAS라 결정적).

**기준선 대비 변화:** 없음(엔진·저장 스키마 미변경).

**알려진 문제·미검증·외부 차단:** 없음. F01은 BLOCKED가 아니라 실제로 완료 상태였다.

**다음 작업 ID / 바로 실행할 첫 행동:** F02 — 실행 중인 dev 서버에서 Claude in Chrome으로 1440×900/390×844/360×800 세 크기의 방송 화면을 인수한다. 과거 세션 기록(D018~D022)에 "CDP 스크린샷이 1568px로 고정되고 `resize_window`가 무시된다"는 반복된 도구 제약이 있으므로, 이번에도 막히면 즉시 BLOCKED로 기록하고 1440×900처럼 되는 크기부터 진행한다.
