# 데이터 갱신 절차 (DATA_UPDATE_GUIDE)

다음 시즌 로스터·실제 경기 기반 평가 데이터를 갱신할 때 따르는 절차. `lib/rosters.ts`(로스터)와 `lib/players/rating-model.ts`(평가 모델)를 대상으로 한다.

## 로스터(소속·이름·사진) 갱신

1. **출처를 실제로 연다.** `docs/claude/REAL_ROSTER_AUDIT.md` §2의 우선순위(①대회 공식 등록 ②팀 공식 발표 ③공식 경기 기록 ④보조 통계 사이트)를 따른다. 검색 엔진 요약만 보고 "확인됨"으로 적지 않는다 — 이 세션의 실수를 반복하지 않는다(§0, WebFetch가 Liquipedia/Fandom에서 전부 차단됐던 경험).
2. `lib/rosters.ts`의 `RosterPlayer`를 수정한다:
   ```ts
   {handle:'새핸들', realName:'실명(공개된 경우만)', role:'MID', status:'starter', note:'선택'}
   ```
   `status`는 `'starter'|'bench'|'academy'|'inactive'` 중 실제로 확인된 값만 쓴다 — "로스터에 등록됨"과 "실제 선발 출전"을 구분한다(§0).
3. 팀 단위 `TeamRosterEntry`에 `sourceUrl`·`confirmedAt`(오늘 날짜, ISO)을 반드시 채운다. 이 두 필드가 비어 있으면 그 팀 데이터는 아직 검증되지 않은 것으로 취급한다.
4. 충돌하는 출처가 있으면(예: 이번 세션의 KT Rolster ADC/SUP, Gen.G Duro 실명) 더 최근에 게시됐다는 이유만으로 하나를 고르지 않는다 — 실제 등록/적용 날짜를 확인하고, 그래도 안 풀리면 `note`에 남기고 `REAL_ROSTER_AUDIT.md` §6 검토 목록에 추가한다.
5. ID 매핑을 지킨다 — 팀 내부 ID(`nva`, `crn`, ...)와 선수 `handle`이 코드 전체를 잇는 유일한 열쇠다. 이름이 바뀌었다고 새 항목을 만들지 말고 기존 항목의 `handle`/`realName`을 갱신한다. 배열 순서나 닉네임 문자열만으로 연결하지 않는다 — `role` 필드로 명시적으로 연결한다(이번 세션에 배열 위치 기반 매핑을 `role` 키 기반으로 바꾼 이유).
6. **사진**: `PLAYER_PHOTO`/`TEAM_LOGO`에 URL을 추가하기 전에 그 URL이 실제로 이미지에 접속 가능한지, 재호스팅이 아니라 원본 서버를 직접 가리키는 링크인지 확인한다. 사용 조건이 불명확하면 추가하지 않는다(빈 채로 두면 이니셜 모노그램으로 자동 폴백 — `app/manager.tsx`의 `PlayerFace`/`Emblem` 컴포넌트, 실패해도 깨진 이미지가 아니라 깔끔하게 폴백됨을 `onError` 처리로 보장).
7. 로스터 인원 제한 확인 — `lib/game.ts`의 `newGame()`은 팀당 7명(선발 5 + 벤치 2)만 만든다. 실제 등록 선수가 이보다 많으면 코드가 조용히 일부를 누락시키는 게 아니라, 어떤 선수를 이번 7명에 포함할지 `status`(starter 우선, 그다음 bench/academy)로 명시적으로 결정한다 — 이 우선순위를 벗어나는 경우가 생기면 그때 `newGame()`의 7명 상한 자체를 재검토할 것(이번 세션엔 상한 자체는 안 건드림).

## 이미 진행 중인 커리어에는 자동 적용되지 않는다 — 왜, 그리고 언제 적용되는가

`lib/rosters.ts` 변경은 **`newGame()`이 처음 실행될 때(새 커리어 생성)만** 반영된다. `lib/game.ts`의 소비 지점(도메스틱 로스터 생성부, 해외팀 `upgradeGame` 백필부)을 보면 두 곳 다 "아직 이 팀/선수가 없을 때만" 실행되므로, 이미 만들어진 커리어의 선수 소속·계약·나이·성장·이적 기록은 로스터 파일을 바꿔도 절대 덮어써지지 않는다 — 이건 우연이 아니라 기존 엔진 구조(§9, "새 커리어에만 적용") 그대로다. **사진·로고**(`PLAYER_PHOTO`/`TEAM_LOGO`)는 한 단계 더 안전한데, `Player`/`Game` 저장 상태에 전혀 저장되지 않고 화면이 그릴 때마다 이름으로 조회한다 — 그래서 사진 URL을 추가/교체해도 기존 세이브 마이그레이션이 필요 없다(코드 경로 자체가 저장 상태를 건드리지 않음).

## 평가 모델(실제 경기 기반 능력치) 갱신

아직 실제 데이터가 하나도 연결되지 않은 상태(`docs/claude/PLAYER_RATING_MODEL.md` §0)이므로, 이 절차는 **처음 실제 데이터를 연결할 때**를 위한 것이다:

1. `lib/players/rating-model.ts`의 `RawMatchObservation[]`을 실제 경기별 기록으로 채운다. 각 항목에 `sourceUrl`이 필수 — 이 URL을 실제로 열어 그 경기 기록을 봤다는 뜻이어야 한다.
2. 표본이 선수당 최소 10경기(낮은 신뢰도) 이상 모일 때까지는 `confidenceForSample()`이 자동으로 `low` 이하로 표시한다 — 이 등급을 임의로 올리지 않는다.
3. `THRESH_FULL_SAMPLE`(현재 40, 미검증)을 실제 표본 분포로 재측정한다 — F27이 `MIN_SAMPLE=6`을 실측(3시즌 scratch 시뮬레이션)으로 정한 것과 같은 방식(감으로 정하지 않기).
4. `BASELINE_BY_ROLE`을 역할별 실제 리그 평균으로 나눠 넣는다(지금은 5개 역할 전부 65로 동일).
5. `GameRating`을 만들고 나서, 기존 `makePlayer()` 경로를 대체하기 전에 **대표 선수 표본(포지션별 2~3명)으로 먼저 검증**한다 — `PLAYER_RATING_MODEL.md` §9의 검증 절차(같은 조합·시드에서 선수만 교체 비교, 숨은 승률 보너스 금지, 약팀도 승산 있는지 확인)를 그대로 따른다.
6. 전체 적용 전에 F15가 쓴 McNemar 페어 CI 방법론(`tests/teamfight-review.mjs`)으로 실제 승률 이동폭을 측정해 "지배적 레버"가 되지 않는지 확인한다.
7. 적용은 F27과 같은 이유로 **새 커리어 생성 시점에만** — 진행 중인 커리어의 선수 성장·능력치를 실제 데이터로 소급 덮어쓰지 않는다.

## 국제대회 팀 확대

LCK 검증·적용이 끝난 뒤에 `INTL_ROSTER`(같은 `TeamRosterEntry` 스키마를 이미 씀)에 위 절차를 그대로 반복 적용한다. 스키마는 이미 공통이라 코드 변경은 필요 없고, 팀별 실제 데이터 수집·검증만 반복하면 된다.

## 체크리스트 (적용 전 항상 확인)

- [ ] 중복 선수·소속 오류·포지션 오류 없는지(같은 `handle`이 두 팀에 동시에 있지 않은지)
- [ ] 모든 팀에 `sourceUrl`·`confirmedAt`이 있는지, 없다면 그 팀은 "미검증"으로 문서에 명시했는지
- [ ] 사진 URL이 실제로 로드되는지(깨진 링크는 폴백되지만, 애초에 검증 없이 넣지 않는다)
- [ ] 미확인 값을 확정 정보처럼 표시하지 않았는지(`status`/`note` 필드로 구분)
- [ ] `tsc --noEmit`, `npm run build`, `tests/management.test.mjs` PASS
- [ ] 기존 커리어(오래된 세이브) 로드 테스트 — 소속·계약·성장이 변하지 않는지 확인
- [ ] 선수 교체가 실제로 드래프트·경기 화면에 반영되는지 브라우저로 확인
