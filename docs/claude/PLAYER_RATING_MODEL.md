# 선수 능력치 모델 (PLAYER_RATING_MODEL)

작업 기준일: 2026-09-16, LCK 실측 연결: 2026-09-17. 이 문서는 "실제 경기 기록 → 게임용 능력치" 변환 계층의 설계를 기록한다. 설계 원본 타입은 `lib/players/rating-model.ts`.

## 0. 현재 상태를 먼저 정직하게 밝힌다

**LCK 50명(+벤치 2명)은 이제 실제 경기 기록에서 나온 보정치가 스탯에 가산된다. 그 외(해외팀, LCK 델타가 없는 값)는 여전히 100% 게임 설계값이다.** `lib/game.ts`의 `makePlayer()`는 팀의 `base`(전력 기준값) + 역할별 고정 편향(`shapes[r]`) + 시드 난수로 6축 스탯을 만드는 것까지는 그대로다(합성 기본값). 2026-09-16 세션에서는 1차 출처(대회 공식 기록·팀 공식 자료)에 접근하는 도구가 막혀 있었지만(HTTP 429/403/402, `REAL_ROSTER_AUDIT.md` §0), 2026-09-17에 Oracle's Elixir의 실제 경기별 CSV(105,133행, `curl`로 직접 다운로드 성공 — WebFetch는 크기 제한으로만 실패했을 뿐 접근 자체는 막혀 있지 않았다)를 찾아 실제로 연결했다. **다만 아래 §1~§9가 설계한 3계층 타입(`RawMatchObservation`→`ProcessedMetric`→`GameRating`)을 그대로 채운 것은 아니다** — `lib/players/lck-2026-ratings.ts`가 같은 원칙(포지션별 정규화, z-score, 표본 수축, 신뢰도 등급, OBJ/MEC 비워두기)을 더 가벼운 "팀·역할별 델타 테이블 + 가산" 형태로 직접 구현했다(§8 참조). `rating-model.ts`의 3계층 타입은 여전히 어디서도 인스턴스화되지 않는다 — 더 엄밀한 원자료 단위 파이프라인이 필요해지면 그때 이 타입들로 옮겨갈 수 있게 남겨 둔 설계다. `app/manager.tsx`의 선수 상세 화면은 이 상태를 항상 "게임 내 평가 — 공식 능력치 아님, 현재는 팀 전력 기반 설계값입니다"라고 노출한다(LCK 델타가 가산된 선수도 동일 라벨 — 실제 기록 보정이 섞여도 "공식 능력치"라 부르지 않는다는 원칙은 그대로 유지).

## 1. 엔진 계약 — 절대 안 바꾼 것

`lib/game.ts`:
```ts
export const STAT_KEYS = ['LNE','TF','OBJ','VIS','MEC','CAR'] as const;
export const STAT_NAMES = ['라인전','한타','오브젝트','시야','메커닉','캐리'];
```
6축의 이름·순서·`Player.stats:number[]`의 배열 위치를 그대로 유지한다. 이 모델은 이 6축에 값을 채우는 방법만 다루지, 새 축을 만들거나 순서를 바꾸지 않는다.

## 2. 계층 분리

```
RawMatchObservation[]  (관측 원자료, 경기 1건당 1개, 출처 URL 필수)
      ↓ 정규화(팀 전력·상대·경기 시간 보정)
ProcessedMetric         (역할별 전처리 지표, 표본·기간·신뢰도 포함)
      ↓ 6축 매핑 + 기준선 수축(shrinkage)
GameRating               (STAT_KEYS 순서의 6개 숫자 + 모델 버전 + 신뢰도)
```
세 계층은 `lib/players/rating-model.ts`에 타입으로 존재한다. 지금은 1번(원자료)이 비어 있어 2·3번도 전부 `confidence:'design-default'`로 귀결된다.

## 3. 6축 ↔ 후보 대리 지표 매핑

| 엔진 축 | 후보 원자료(§6 예시, 전부 후보일 뿐 확정 아님) | LCK에 실제로 연결했나 (2026-09-17) |
|---|---|---|
| LNE(라인전) | 10분 CS·골드·경험치 차이 | 예 — `golddiffat10` |
| TF(한타) | 전투 관여·생존·자원 대비 기여 | 예 — 킬관여율 `(kills+assists)/teamkills`(생존은 미반영) |
| OBJ(오브젝트) | 목표 주변 참여·확보 관련 기록 | 아니오 — CSV에 개인 단위 대응 지표 없음(팀 단위 드래곤/바론 수만 있음) |
| VIS(시야) | 시야 점수·역할·경기 시간 정규화 | 예 — `vspm`(분당 시야점수) |
| MEC(메커닉) | **대응하는 흔한 공개 지표가 없음** — 대리 지표를 억지로 만들지 않고 `mechanicsShare`를 항상 `null`로 둔다 | 의도적으로 미구현 |
| CAR(캐리) | 받은 자원 대비 실제 딜 기여 | 예 — `damageshare`(받은 자원 대비 비율까지는 아직 아님, §8 한계) |

"팀플레이"(합류·보호·판단)는 기획 문서의 후보 축이었지만 공개 경기 기록이 직접 관측하지 못하는 정보다 — 다른 숫자로 대체해 "직접 관측한 것처럼" 보여주지 않는다(사용자 지시 §6). 이 축은 이 세션에서 아예 구현하지 않았다.

## 4. 포지션 정규화

정글·서포터의 딜량을 원딜 기준으로 채점하지 않는다 — `carryShare`는 `damageShare`를 그대로 쓰지 않고 `goldShare`(받은 자원) 대비 비율로 계산하도록 설계했다(코드 참조). 역할별 기준선(`BASELINE_BY_ROLE`)도 역할마다 다른 값을 가질 수 있게 타입을 만들어 뒀다 — 지금은 5개 역할 전부 65로 동일하게 넣어 뒀는데, 이건 **실제 데이터가 없어 구분할 근거가 아직 없기 때문**이며, 실측이 들어오면 역할별로 갈라야 한다(§7 참고).

## 5. 기본 실력 vs 컨디션 분리, 표본 수축(shrinkage)

`shrinkTowardBaseline(observed, role, sampleGames)`은 표본이 적을수록 역할 기준선 쪽으로 강하게 당긴다(§7 "소수 경기의 좋은 성적만으로 최고 능력치를 받지 않게"). 표본 40경기를 "거의 전부 신뢰" 기준(`THRESH_FULL_SAMPLE=40`)으로 잠정 설정했는데, **이 숫자는 이 세션의 다른 임계값들(F27의 `MIN_SAMPLE=6`, F21의 밴/픽 가중치)과 달리 아직 실측으로 보정하지 못했다** — 실제 원자료가 들어오면 반드시 재측정해서 바꿀 것(감으로 정한 채로 두지 말 것).

기본 실력(수축된 장기 지표)과 최근 컨디션(`Player.form`, 이미 존재하는 필드)은 이 모델에서 분리된 채로 유지한다 — `GameRating`은 장기 기본 실력만 담당하고, `form`은 손대지 않는다. 같은 최근 성적이 양쪽에 중복 반영되지 않도록, 실제 데이터 파이프라인을 연결할 때는 `form` 갱신 로직과 `GameRating` 재계산 로직이 같은 "최근 N경기" 창을 공유하지 않게 할 것(다음 단계에서 실제로 연결할 때 지켜야 할 제약으로 여기 기록해 둔다).

## 6. 신뢰도(confidence) 등급

`confidenceForSample(games)`: 0경기=`design-default`, 1~9경기=`low`, 10~39경기=`medium`, 40경기 이상=`high`. UI에 이 등급을 노출할 때는 숫자 자체보다 "표본 부족"이라는 사실을 우선 보여준다(F27의 관측 승률 UI가 이미 쓰는 "표본 부족" 패턴과 동일한 정직성 원칙).

## 7. 잠재력·성향·성장 속도

경기 기록만으로 확정하기 어렵다고 판단해 이 모델(`GameRating`)과 완전히 분리한다. 이미 존재하는 `lib/players/temperament.ts`(F18, id 해시 기반 순수 함수)·`Player.pot`(잠재력, `makePlayer`에서 스탯+노이즈로 생성)가 이 역할을 맡고 있고, 이번 세션에서 건드리지 않았다 — 둘 다 "게임 설정값"이며 실존 선수의 실제 잠재력이나 성향을 추정한 값이 아니라는 점을 명시한다. 실존 선수의 성격·사생활에 대한 추측은 만들지 않았다.

## 8. LCK는 이렇게 연결했다 (2026-09-17)

`RawMatchObservation`/`ProcessedMetric`/`GameRating` 3계층을 문자 그대로 채우는 대신, 같은 원칙을 지키는 더 단순한 경로를 택했다 — `lib/players/lck-2026-ratings.ts` + `lib/game.ts`의 `newGame()`:

1. Oracle's Elixir 2026 CSV(`league==='LCK'`)에서 역할별(`position`) 전체 표본으로 기준선(평균·표준편차)을 구한다 — 이게 `BASELINE_BY_ROLE`의 실측 버전이다(역할별로 실제로 다른 값).
2. 축 매핑(§3)을 그대로 써서 선수별 평균을 계산하고, 기준선 대비 z-score(±2.5 clamp) → `min(1,games/40)` 표본 수축(§5의 `shrinkTowardBaseline`과 동일 원리, 구현은 독립) → ×4로 "델타"(최대 ±10점)를 만든다.
3. 이 델타를 `RawMatchObservation`처럼 저장하지 않고 `LckRatingEntry{delta,games,confidence,team,role}` 형태로 핸들별 최종 결과만 저장한다 — 원자료 CSV(70MB)는 저장소에 없다(재현 절차는 `DATA_UPDATE_GUIDE.md`).
4. `makePlayer()`가 만든 합성 스탯 위에 `newGame()`이 이 델타를 **가산**한다(대체 아님) — `LCK_ROSTER`로 실명을 오버레이하는 지점과 같은 곳, **새 커리어 생성 시점에만** 실행된다(§9, 기존 커리어 보호는 로스터 오버레이와 동일한 구조적 보장).
5. `tests/real-roster.test.mjs`가 대표 선수(Chovy)로 `lckStatDelta()`가 저장된 값을 그대로 반환하는지, 델타 가산 후 모든 LCK 선수 스탯이 클램프 범위(15~96) 안에 있는지 검증한다.

`rating-model.ts`의 3계층 타입은 이번엔 쓰이지 않았다 — 원자료(경기 1건 단위) 저장이 실제로 필요해지거나(예: 특정 경기 하나를 근거로 보여주고 싶을 때), 축 매핑을 CSV 컬럼이 아닌 다른 출처에서 다시 만들어야 할 때 이 타입들로 옮겨가면 된다. 해외팀(`INTL_ROSTER`)은 아직 이 델타 테이블이 없다 — LCK와 같은 절차를 반복하면 된다(`DATA_UPDATE_GUIDE.md` "국제대회 팀 확대" 참조).

## 9. 검증 절차(적용될 때 반드시 지킬 것)

- 같은 조합·전술·시드에서 선수만 교체해 비교 — 전체 승률뿐 아니라 그 선수의 강점 축에 대응하는 행동 지표(라인전 골드차, 오브젝트 참여율 등)가 실제로 달라지는지 확인.
- 유명 선수·강팀에 숨은 승률 보너스를 넣지 않는다. 현실 순위를 재현하려고 능력치를 역산하지 않는다 — F12(감독 지시)·F18(성향)에서 이미 지킨 "지배적 레버 금지" 원칙과 동일.
- 밴픽·숙련·컨디션·전술로 약팀도 승산이 있는지 검증(F15가 이미 쓴 McNemar 페어 CI 방법론 재사용 가능).

## 10. 알려진 한계 (지금 시점)

- LCK 50명+벤치 2명만 실측 델타 연결. 해외팀(`INTL_ROSTER`)은 여전히 0건 — §8 절차 미반복.
- OBJ·MEC 두 축은 LCK 델타에도 없음 — CSV에 대응 지표가 없어 의도적으로 비움(대리 지표 금지 원칙).
- 델타 계산에 쓴 `THRESH_FULL_SAMPLE`(40, shrink 분모)은 `rating-model.ts`의 동명 상수와 같은 값이지만 별도 구현이고, 둘 다 여전히 실측 재보정 전(F27 `MIN_SAMPLE=6`처럼 표본으로 재측정한 적 없음).
- `rating-model.ts`의 `BASELINE_BY_ROLE`(5개 역할 전부 65)은 실제로는 쓰이지 않는 값이다 — LCK 델타는 별도 구현(`lck-2026-ratings.ts`)이 CSV에서 직접 역할별 기준선을 구해서 쓴다. `rating-model.ts` 자체는 여전히 `Player`/`Game` 타입에 연결돼 있지 않다(독립 모듈로 남음, §8).
- "기본 실력 vs 최근 컨디션" 분리(§5)는 델타(장기 season 표본) 쪽만 구현됨 — `Player.form`과 같은 최근 N경기 창을 공유하지 않는다는 제약은 지켜지지만, 델타 자체에 "최근 컨디션" 신호를 별도로 반영하지는 않는다(2026 Cup 최근 스테이지 41경기 표본을 op.gg에서 확인은 했지만, 별도 레이어로 만들지는 않음 — 다음 단계 후보).
